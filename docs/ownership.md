# Ownership and recovery

Definitions are identified by their vault-relative path. Existing schemas and renderer output bytes are unchanged. A receipt has `version: 1`, `definitionPath`, `outputPath` and a lowercase SHA-256 `digest` of the authorised saved output. Missing receipts cannot affect display or compilation.

A state table's sole canonical ownership comment must be on its own final line (LF, CRLF and an omitted final newline are accepted), with the exact URI-encoded definition path. A substring, duplicate comment, conflicting owner or non-canonical encoding is rejected. Legacy SVGs have no ownership proof. Explicit adoption validates the declared destination, asset type, all current source/definition collisions and any former ownership. Consent is a one-use in-memory inspection bound to the asset and definition digests. The final write rechecks those digests. The dialog has Cancel, raw-content inspection and Open existing output; it never executes SVG markup.

An existing receipt must parse and match the output digest/path. A corrupt receipt or externally changed owned asset is blocked even by adoption: recover the original asset/receipt, or choose a new output path. Adoption is not an override for another report. Path repair is permitted only when the former definition is absent and no current definition competes for the destination. It still requires an explicit confirmation. Receipts do not carry hidden report configuration.

Before replacement, a verified copy is created adjacent to the output as `<output>.murmuration-report-backup` (then `.1`, `.2`, etc.). Backups contain the exact original bytes. They are not Markdown observations and are not deleted automatically. Back them up with the vault; inspect/recover them manually if needed. Undo is not provided; copying a backup back to its original location is a deliberate recovery action. Restore the corresponding receipt or explicitly resolve ownership before another generation.

The coordinator computes output in memory, checks current Markdown definitions and observations from fresh file reads, snapshots content and inventory, then rechecks before mutation. All its requests are serialised. `Vault.process` performs compare-and-replace for text files; creates check both the vault index and adapter before writing. Every output and receipt is read back before success. Receipt failure is generation failure, with best-effort conditional compensation and explicit recovery paths. Only API-confirmed replacements are eligible for conditional compensation; rejected writes are not proof of a commit. Ambiguous completion retains files and recovery copies. Newly created files are never deleted on failure because Obsidian has no atomic compare-and-delete. Disabling Reports cancels queued work and subsequent normal writes; guards also run inside the native process callback. Re-enabling shares an app-scoped queue with unfinished work from the previous instance.

Obsidian offers no multi-file transaction or vault-wide lock, and delete has no compare-and-delete primitive. The SDK also lacks exclusive create and external-writer locks. Rechecks cannot prevent an external sync write between all individual operations; conditional rollback cannot guarantee preservation against a writer outside the SDK lock. Abrupt process termination can leave a new output without a receipt, a mismatched pair, or a backup requiring recovery. These fail safely on subsequent regeneration instead of being reported as ownership proof. The plugin does not claim crash-atomic generation. Empty output directories may remain after a failure.

The generation coordinator reads the Markdown inventory for collision safety, including when metadata caches lag. This work happens only for explicit commands; it is not an event-driven index. An unreadable frontmatter note blocks generation because its possible output declarations cannot safely be inferred. Portable path validation and case/Unicode-normalised collision comparisons prevent ambiguous destinations. Native vault events only invalidate snapshots; they never generate reports. A concurrent Markdown edit anywhere in that inventory may require retry. The manager uses a bounded in-memory catalogue, while explicit mutation-time checks still read fresh declarations.
